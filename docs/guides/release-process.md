# Weekly Release Process

This guide describes the maintainer checklist for publishing a new template release.
The full process should take under 2 hours per week.

---

## Prerequisites

- You have write access to the repository and can push tags.
- All stories for the release are in `review` or `done` status in `sprint-status.yaml`.
- CI is green on `main`.

---

## Weekly Release Checklist

### 1. Review merged PRs since last tag

```bash
# List commits since the last tag
git log $(git describe --tags --abbrev=0)..HEAD --oneline
```

Check that all changes follow [Conventional Commits](https://www.conventionalcommits.org/).
If any commit message is malformed, it will be omitted from the CHANGELOG — fix with `git commit --amend` before releasing.

### 2. Choose release type

| Change type                        | Command                 |
| ---------------------------------- | ----------------------- |
| Bug fixes only                     | `npm run release:patch` |
| New features (backward compatible) | `npm run release:minor` |
| Breaking changes                   | `npm run release:major` |

> **Before a MAJOR release:** Create a migration guide following the template in
> [docs/guides/migration-guide-template.md](./migration-guide-template.md).
> Also run `npm run compat:check` to surface any user code that imports template-owned paths.

### 3. Run the release command

```bash
npm run release:minor   # or release:patch / release:major
```

This command:

1. Bumps the version in `package.json`
2. Creates a git commit `chore(release): v1.x.x`
3. Pushes the commit and tag to `origin/main`

The `release.yml` GitHub Actions workflow then automatically:

- Generates `CHANGELOG.md` from conventional commits since the previous tag
- Commits the updated `CHANGELOG.md` back to `main`
- Creates a GitHub Release with the CHANGELOG entry as release notes

### 4. Verify the GitHub Release

1. Open the [Releases page](../../releases) on GitHub.
2. Confirm the new release is marked `Latest`.
3. Verify the release notes match the CHANGELOG entry for this version.
4. Confirm the Security section is present if any `fix(security):` or `security:` commits were included.

### 5. Share with the community

- Post the release link in the project's community channel / GitHub Discussions.
- Highlight any breaking changes or security fixes prominently.

---

## CHANGELOG Format Reference

The CHANGELOG is auto-generated by `npm run changelog` (`conventional-changelog-cli`).
Section order:

1. `⚠ BREAKING CHANGES` — commits with `!` or `BREAKING CHANGE:` footer
2. `Security` — commits typed `fix(security):` or `security:`
3. `Features` — `feat:` commits
4. `Bug Fixes` — `fix:` commits (excluding security scope)
5. Other sections (Docs, Chores, etc.)

---

## Rollback

If a release is broken:

```bash
# Revert to previous tag (e.g., v1.2.0)
git checkout v1.2.0
```

The previous tag remains in git permanently. GitHub Release can be unpublished via the UI if needed.
